## Architecture
- Unit of work: "the unit of work is a 'changeset,' an entry in a write-ahead log. ... where a git commit stores a pointer to the tree, a changeset stores a list of the files that changed relative to its first parent, along with content-addressed pointers to the compressed file contents in blob storage. Changesets are created server-side and are available everywhere, instantly."
- Footnote 1: changed files are stored "relative to the first parent of a merge ... people only care about history or blame for commits on the main line in trunk-based development in a monorepo." (i.e., a deliberate loss of information for merge commits.)
- No packfiles, locks, cross-server coordination; "no refs to move around". Refs are "a compare-and-swap on a single Spanner row that happens separately from creating changesets" and discouraged "except for the main ref or release branches".
- Derived data: "A changeset records only what's changed, so on its own, it can't quickly answer questions like who last edited a line or which commits affected a file. ... Scion builds additional data structures ... file blame and path history and skip lists for the commit graph. We call everything that isn't directly part of the changeset 'derived data,' and we compute it all through one generic mechanism. Each type of derived data is defined recursively, so its value for a changeset is computed from its values for that changeset's parents." Three benefits stated: add a type easily; choose eager or deferred per type; clients never see the internals so they can be optimised. Examples added later: "indices for performing copy detection or path-based file search."
- Content addressing for scaling: "All source control data is content-addressed, so a piece of data never changes once it's stored, and any server can cache it without checking with the others. ... They are essentially large caches that can also compute derived data on the fly and write the results back to Spanner."
- Fetch protocol: "Scion's negotiation doesn't tell the server what the client already has; instead, it operates exclusively on trees and blobs the client wants. Starting from a root tree, the client checks its local store for missing trees and requests them recursively, then repeats the process for blobs." Sparse and virtualised checkouts "don't need special support, because the client simply doesn't ask for trees it doesn't want." Tiers: scion-daemon (per node) -> scion-cache (regional) -> scion-server (authoritative; Spanner / cloud storage).
- Agent-facing API: "all of the source control queries the client uses are also exposed via API, so in many cases jobs don't need a local repository at all." Server answers history, blame, commits, merges, rebases; "a CI job that needs the diff between a commit and its merge base ... can ask the server for it. The same goes for writes." Used for "automated bisect and revert pipelines".
- Principles: clients always online; client-server asymmetry (client "can compute very little on its own"); horizontal scalability ("no fully materialized copy of the repo anywhere, even on the server"); "The cost of creating a commit and updating its downstream data structures has to scale with the size of the change, not the overall size of the repo".

## Numbers and what they compare
- Workload: ~2,500 merged changes/day (May 2026), over 30,000/day (September). Main-branch history "almost 100 GB", compressed working copy "over 25 GB", "on the order of 25 million code checkouts per day for CI" (excluding dev environments, agent sandboxes, research jobs), "over 600 PB of git traffic per day" if fetched naively. "At our peak, we operated several hundred internal git mirrors".
- THE 200x FIGURE: "Our Scion infrastructure footprint is now 200x smaller than our previous git mirroring infrastructure in terms of CPU and memory requirements." So: total fleet footprint (CPU and memory) of Scion vs the prior fleet of git mirrors plus seeds, for the same checkout-serving workload. It is NOT a per-query, per-diff, per-checkout or algorithmic speed-up and not a comparison to stock git on a single repo. No measurement method or period is given.
- Related: "CI and research jobs check out code two orders of magnitude faster (in seconds rather than minutes)"; "CI alone realized a 25% CPU capacity win"; "Each tier ... maintains a cache hit rate of over 99%". No baseline detail beyond that. A chart "Observed performance improvements on native Scion repos" exists but its data is not in the text.
- Other numbers: seven-person team; five-month migration "while the volume of code merged per day increased by 10x"; a Claude-rewritten ingestion pipeline "consumed 20x less memory and was 4x faster".

## Limitations and prior-art credit (all that the post gives)
- "Scion is by no means a suitable replacement for git for general use. The concepts ... really only make sense for truly enormous monorepos, with either tens of thousands of engineers or swarms of agents."
- Anthropic's token spend "far exceeds what any other business would realistically want to spend."
- Hard to productise: "companies would need to migrate every piece of the development lifecycle ... requires its own code review, code search, and CI. Our internal versions ... are highly bespoke". No public release.
- No ablation or independent measurement; the 200x is self-reported and unbroken-down.
- Agents violated constraints (e.g., "brute force looking up when a change merged to main by linearly reading the commit log"); adversarial review caused over-engineering. Merge queue abandoned: "concurrent changes can conflict, but Claude can typically fix these conflicts faster than humans can even identify them." (so conflict is handled post-merge.)
- Prior art: "Source control for huge monorepos has prior art, notably Google's Piper and Meta's Sapling" and footnote 2: "Specifically, the server component of Sapling, Mononoke. It pioneered many of the techniques we use in Scion, in particular the Bonsai data model." The post also acknowledges "the git community has spent nearly two decades scaling the platform" and suggests git servers could adopt Scion-like RPCs.
- NOT in the post: any claim about diff algorithms, content-defined chunking, rename/move detection quality, or edit scripts. The only copy-detection mention is "new indices for performing copy detection" as a derived-data type.

## Lessons for the provenance DAG
- Scion stores only the delta relative to the first parent and derives everything else: a HISTORICAL delta is the primary record; optimal/presented views are derived data computed lazily from parents. That matches our three-delta split, but note Scion discards merge-parent deltas (footnote 1), so historical truth is deliberately partial. We must state what we drop.
- "Recursively defined from parents" is the Adapton recipe on a DAG: value(v) = f(inherent(v), derived(parents(v))). Cost "scales with the size of the change" only because each derivation reads parents' derived values rather than the whole tree.
- The 200x number tells us nothing about delta quality; it is a serving-infrastructure result. Do not cite it as evidence for a diff or correspondence design.
- Scion OWNS the write path, so each changeset's parent and file list is authoritative. We do not own websites (see SYNTHESIS).
