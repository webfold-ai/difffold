## 1. Contract table for web monitoring (five concerns kept separate)

Quotes are from the doc pages listed in exa.md and firecrawl.md. "Guarantee" means what the text promises, not what the product might do.

| concern | Exa (quoted) | Firecrawl (quoted) | gap for us |
|---|---|---|---|
| DISCOVERY of new pages | Monitors: "executes the configured search, filters by time, removes results or findings the monitor has already returned, and sends the new output to your webhook." Min interval 1 hour; "each run may be delayed by up to 30 minutes"; overlapping runs are cancelled. Index refresh: "timing that varies by source and how often a page changes." | Search monitor: "It's discovery rather than diffing." Dedup "keyed on the canonical URL alone ... one real-world event reported across many article URLs alerts once per URL, not once per event." Crawl target bounded by `limit` and `maxDiscoveryDepth`. | Neither promises recall, a coverage bound, or time-to-discovery. Exa gives no dedup key. Both dedupe by URL, so "new URL" is not "new entity". We need discovery events recorded as claims ("seen in run R under query Q and limits L") not as facts about the web. |
| FRESHNESS OF OBSERVATION | `maxAgeHours` (-1 to 720): "Omit: Use cached content when available and fetch the page when needed ... 0: Always fetch fresh content. -1: Only use cached content." Per URL `statuses` with `source` in {cached, crawled} and `error.tag` / `httpStatusCode`. `livecrawlTimeout` default 10000 ms. | Monitors: "monitor-triggered scrapes default `maxAge` to `0`, so each check re-scrapes discovered pages fresh". Change tracking: "Requests with `changeTracking` bypass the index cache. The `maxAge` parameter is ignored." Each check records `previousScrapeAt`. | Freshness is a request-time policy, not an attested fact. Exa's result schema (as read) carries no observed-at time, so `cached` has unknown age. Neither says what a "fresh" fetch means for JS-rendered or personalised pages. We must store `observed_at`, the policy requested, and the source (cache vs live) on every observation. |
| CONTENT CHANGE of a known page | none for known pages. `snapshotAsOf` reads "the newest stored version of each page as of this instant" from "stored versions only", but no diff API was found. | `changeStatus` in {new, same, changed, removed}. "compares pages via their markdown content"; "resistant to whitespace and content order changes"; `git-diff` and `json` modes; JSON mode is LLM extraction at "5 credits per page"; a JSON monitor "still report[s] `same`" if only surrounding markdown changed. | Firecrawl's unit is markdown after its own extractor; "same" is relative to extractor settings ("different `includeTags`, `excludeTags`, or `onlyMainContent` settings ... produces unreliable comparisons"). No guarantee that "same" means the interaction state or HTML is the same, nor that the LLM extraction is stable run to run. Our ContentId must be keyed by (representation policy, extractor version), and "unchanged" is only defined for that key. |
| ENTITY CORRESPONDENCE | Websets have typed entities (company, person, article, paper, custom) for search targeting; the docs I read give no identity-over-time rule. | "Previous scrapes are matched on exact source URL, team ID, `markdown` format, and `tag`." Moves appear as `removed` plus `new`. | Both define identity as the URL string (Firecrawl) or leave it undefined (Exa). Nothing ties a page to a person/product across URL change, redirect, or restructure. OccurrenceId assignment is entirely ours; it must be labelled inferred and carry its evidence. |
| DEPENDENCY INVALIDATION | none documented. `refresh` Webset monitor runs exist but their change test is unspecified. | none documented. A `goal` plus LLM judge says whether a diff was "meaningful", which is a relevance filter, not a dependency graph. | Neither vendor offers "which downstream record, embedding, or agent precondition is stale". This row is entirely ours, and Adapton (edge labels, dirty marking, early cutoff) is the model. |
| (cross-cutting) ACQUISITION FAILURE vs REMOVAL | per-URL `status: error` with `tag` and HTTP code; crawler "does not attempt to bypass logins, paywalls, or CAPTCHAs" but no named login-wall class was found. | `error` is "The page could not be checked", separate from `removed`. But website-monitor `removed` = "A page from the previous check was no longer discovered", which can be caused by crawl limit/depth, de-linking, or robots. `visibility: hidden` marks "URL works but is no longer linked". | Neither separates "positively observed gone (404/410/tombstone)" from "not found this time". A soft login wall returned as HTTP 200 would register as a content change. We need three outcomes: observed-content, observed-absence (positive evidence), not-observed (with reason). Removal is only ever the second. |

## 2. Mapping Scion / Mononoke ideas to our observation service

Key asymmetry: Scion and Mononoke OWN their changesets. A commit is an authoritative event created on their write path, with explicit parents, so "what changed relative to parent" is a fact. A crawler owns neither the website nor its history. An observation is a SAMPLE of a process we cannot see: the interval between two observations may hide intermediate states, cancelling edits, and renames. Scion's changeset = historical delta by construction; our corresponding object is an "observed transition", which is only a bound on history.

| idea | in Scion / Mononoke (source) | our service | what changes because we do not own the source |
|---|---|---|---|
| changeset as WAL entry | "a list of the files that changed relative to its first parent, along with content-addressed pointers" (Scion); Bonsai flat path-to-change list with parents. | VersionId = immutable observation record: (occurrence, observed_at, request policy, acquisition outcome, payload ContentId, parent observation). Append-only, lock-free. | The record must include failures and the fetch configuration; a changeset never fails to "occur", an observation can. Parent = previous observation, not a causal predecessor. First-parent-only storage (Scion footnote 1) is acceptable for us because there is one lineage per occurrence, but merges (page merges, URL consolidation) need explicit multi-parent edges. |
| content addressing | Blake2b ContentId; "a piece of data never changes once it's stored, and any server can cache it". | ContentId over canonical representation, keyed by representation policy and extractor version. | Hash equality means "our extractor produced the same output", not "page unchanged". Include policy in the key or equality is meaningless. |
| derived data, recursively maintained | "its value for a changeset is computed from its values for that changeset's parents"; eager-or-deferred per type; Mononoke `derive_single(changeset, parents' derived data)` with a declared dependency DAG; derived data "not included in content-addressed hashes". | optimal delta, presented delta, extractions, entity correspondences, index records are derived types over observations. Dependency invalidation = Adapton-style dirty marking over the derived-data DAG with early cutoff on ContentId. | Derived values may be non-deterministic (LLM extraction, matcher with thresholds). So the derivation key must include extractor/matcher version and config, and results must be stored as versioned claims, never as hash-addressed inherent data. |
| lazy materialisation, sparse/virtual access | client "simply doesn't ask for trees it doesn't want"; virtualised checkouts; "no fully materialized copy of the repo anywhere". | Return handles (VersionId + delta handle) and expand on demand; fetch bodies lazily from the observation store. | We can be lazy about reading our own store, but not about re-acquiring from the web: freshness requests cost fetches and politeness budget. Lazy must not silently mean stale; every read states which observation it used. |
| agent-facing APIs | all client queries "exposed via API"; jobs need no local repo; diff to merge-base "can ask the server for it". | Queries: "has occurrence X changed since observation V", "what depends on X at version V", "history of X", all returning delta handles with provenance. | Answers must carry observation time and an acquisition status, otherwise an agent precondition check ("is state still as I saw it?") may be answered from a stale sample. |
| copy/rename info | Bonsai records copy-from explicitly (committer assertion). Scion lists "copy detection" as a derived index (inferred). | Explicit edges only when the site gives them (redirect, canonical link, sitemap move, structured id). Otherwise inferred correspondence stored separately. | A site-provided signal can be wrong or malicious; store who asserted it. |

What neither Scion nor Mononoke supplies: a durable entity id across renames (Bonsai has copy-from edges, not an OccurrenceId). So OccurrenceId is ours to design, with no prior art in these two systems.

## 3. Claims in paper/paper.md Sections 2.4 and 4 (plus the two dependent ones) against my reading

CONFIRMED
- 2.4: rsync "minimises transferred bytes with rolling and strong checksums, not edit count or readability". Report text: only unmatched data is sent; one round trip; the problem is diffing when "both files are [not] available on the same machine".
- 2.4: Scion "describes server-side changesets, content-addressed storage and recursively maintained derived data". All three are in the post, nearly verbatim.
- 2.4: credits Mononoke/Bonsai (footnote 2); "states that it is not a general Git replacement" ("by no means a suitable replacement for git for general use").
- 2.4: "roughly 200 times smaller CPU and memory footprint relative to its earlier Git mirroring" and "a system-level result, not a faster diff algorithm". The 200x is the infrastructure (CPU+memory) footprint versus the earlier git-mirror fleet, self-reported with no method.
- 2.4: press report "unconfirmed by OpenAI". TechRadar: "OpenAI has not publicly confirmed the project." It says nothing about diff methods.
- 4: Exa "distinguishes indexed results from fresh retrieval through a maximum content age" (`maxAgeHours`). Firecrawl "documents markdown and structured-field comparison" (git-diff and json modes).
- 3 (line 226): arXiv:2604.12696 exists (Albert, LCE of a dynamic string, CPM 2026) and does claim constant parallel time with O(n^epsilon) work on a CRCW PRAM.

WEAKENED OR NEEDING QUALIFICATION
- 2.4 two-line contrast ("snapshot comparison: infer what changed" vs "incremental maintenance: preserve changes and propagate their consequences"). Adapton does not preserve changes as objects. It preserves a dependency graph and, at repair time, COMPARES values to edge labels (early cutoff), which is snapshot comparison at node granularity. The "known change" in Adapton is just the outer layer's `set` marking edges dirty. So the opposition is too clean; the accurate point is that maintained dependency structure confines comparison to dirtied nodes.
- 2.4 groups "Self-adjusting and demand-driven incremental computation (Adapton ...)" as one thing. Adapton's contribution is to differ from self-adjusting computation: that is eager and totally ordered; Adapton is lazy with a partial-order graph, and reports being 1.5x to 3.5x slower when all output is demanded.
- 2.4 "Large source-control systems follow the same logic" as "preserve changes". Scion stores the diff against the FIRST parent only (footnote 1: a deliberate loss) and lists copy detection as a derived index, i.e. renames/moves are inferred after the fact there. Bonsai records copy-from explicitly. So these systems support "record the delta at the write path" strongly, "a move is an event" only weakly (Bonsai yes, Scion no).
- 2.4's account omits the post's own limitations (bespoke, requires migrating review/search/CI, extreme token spend, no measurement method), and Piper/Sapling credit. The paper only needs one of those clauses, but "credits Meta's Mononoke and Bonsai" is accurate only via footnote 2; the main text credits Piper and Sapling.
- 2.4 "unconfirmed by OpenAI" is fine, but the TechRadar piece is dated 2026-03-11, is itself "Via Tom's Hardware", and says "reportedly developing an internal code repository platform", not merely "exploring". Low-value evidence; I would drop it or keep it to a clause.
- 4 web-monitoring row: "A failed fetch, a login wall or a timeout is an acquisition failure and never a deletion." This is normative, not something the vendors guarantee. Exa reports per-URL error tags; Firecrawl has an `error` status but defines `removed` in crawl monitors as "no longer discovered", which conflates deletion with limit/depth/de-linking, and neither documents a login-wall class. State it as a requirement we impose, with the vendor gap cited.
- 4: "Exa distinguishes indexed results from fresh retrieval": true for requests, but the response gives only `source: cached|crawled`, not an observation time, so freshness is not attested after the fact.
- 4: Firecrawl's "structured-field comparison" is LLM extraction (5 credits per page), keyed to exact URL and team; not a deterministic structural diff.

NOT CONTRADICTED BUT UNSUPPORTED BY THESE SOURCES
- Table row "dependency graph on deltas" (index and answer invalidation) and "relevant-state revalidation" for agent preconditions: no vendor documents either. Adapton supports the mechanism in principle (edge labels, dirtying, cutoff), but only for pure functional computation inside one process, with no external-sources story.
- 6.5 bound T = O(f(b) r + k): the nearest published form is Acar's trace stability, "O(f(n) log f(n)) time, in general, and ... O(f(n)) in certain cases" where n is a TRACE DISTANCE, conditional on stability. That supports stating the cost in terms of a distance between maintained structures, and warns that the bound is only good for stable algorithms.

## 4. Three design consequences that matter most
1. An observation is not an event. VersionId must be a record of an attempt (observed_at, request policy such as maxAge, cache-vs-live source, acquisition outcome, extractor version, payload ContentId). Absence is stored only on positive evidence; otherwise store "not observed, reason".
2. Entity correspondence is ours and is inferred. Neither vendor goes beyond URL equality, and Bonsai gives only per-commit copy-from edges. OccurrenceId assignments are claims with provenance (site-asserted vs matcher-inferred, matcher version), kept outside the content hash.
3. Derived data needs Adapton-style edge labels. Key every derived value by (input ContentIds, extractor/matcher version, config); dirty on input ContentId change; cut off when the re-derived ContentId equals the old one. This is the only way to get "changed HTML does not imply changed extracted knowledge" and to cope with non-deterministic LLM extraction.
